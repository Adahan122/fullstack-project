## Как senior разработчик отвечает (2-3 фразы на каждый)

---

### ❓ "Почему React, а не Vue/Angular?"

React — это стандарт рынка. 80% компаний используют React, поэтому навыки максимально востребованы. Экосистема огромная, любую задачу можно решить готовой библиотекой. Vue/Angular хороши, но React выигрывает масштабом и community.

---

### ❓ "Почему Vite вместо Webpack?"

Webpack требует 200 строк конфига, Vite работает из коробки. HMR в разработке — миллисекунды против секунд. Это критично когда разрабатываешься весь день. Для production результат похож, но опыт разработки — небо и земля.

---

### ❓ "Как устроена аутентификация?"

JWT токены. Пользователь вводит логин/пароль → бэкенд проверяет → отправляет JWT → браузер хранит в localStorage → отправляет токен с каждым запросом → бэкенд проверяет валидность. Это стандарт для REST API.

---

### ❓ "Как разделили код между фронтом и бэком?"

Правило один: **все что касается логики и данных — на бэке, все что касается UI — на фронте**. Бэк никогда не доверяет фронту, переделывает всю валидацию. Фронт может валидировать для UX, но это не безопасность.

---

### ❓ "Что такое debouncing в поиске?"

Пользователь печатает «сп» → ждем 500мс → если он больше не печатает → отправляем запрос. Если печатает дальше, счетчик рестартует. Экономит огромное количество запросов. Вместо 50 запросов за 5 букв — 1 запрос.

---

### ❓ "Как обеспечена безопасность?"

CORS — контроль доступа, JWT — безопасные токены, bcrypt — пароли захеширован, HTTPS — шифрование в пути, валидация на бэке — никогда не верим фронту. Это многоуровневая защита.

---

### ❓ "Как развертывали?"

Локально: `docker-compose up` → контейнеры поднялись → работает. Production: GitHub → Render видит push → автоматически пересобирает образ → деплоит → live. Zero downtime deployment.

---

### ❓ "Какие сложности при разработке?"

CORS ошибки поначалу (просто конфиг бэка). Context API справляется, но если б проект был в 10 раз больше — переходили б на Redux. Оптимизация бандла Vite. Мобильная версия требовала времени. Но это обычные задачи.

---

### ❓ "Что ты выучил?"

Full-stack разработку. Docker. REST API архитектуру. Security. Как правильно разделить ответственность между слоями. Как дебагить асинхронный код. Как думать как архитектор, а не просто кодер.

---

### ❓ "Какие улучшения можно добавить?"

Payment gateway (Stripe/PayPal). Elasticsearch для быстрого поиска на миллионах товаров. WebSocket для real-time уведомлений. Redis для кэша. Автоматические тесты (Jest, Cypress). Monitoring (Sentry). ML рекомендации. Все это в очереди.

---

### ❓ "Почему Docker?"

Один контейнер — везде одинаково. На моем ноутбуке, на машине Вани, на production сервере. Без Docker — зависимости конфликтуют, версии расходятся, работает на одной машине и не работает на другой. Docker убирает фразу «ну у меня же работает!»

---

### ❓ "Почему Node.js?"

Я уже писал JavaScript на фронте, Node позволил писать бэк на том же языке. Экосистема NPM — для любой задачи есть пакет. Express минималистичен, ничего лишнего. Non-blocking I/O идеален для I/O-heavy приложений (БД, API).

---

### ❓ "Как тестировали?"

Вручную во время разработки + ESLint проверяет синтаксис + DevTools браузера для дебага + Postman для API. Идеально было бы Jest + React Testing Library + E2E на Cypress, но времени не хватило. Это для production версии.

---

### ❓ "Что такое Context API?"

Глобальное состояние без prop drilling. Вместо того чтобы передавать данные через 10 слоев компонентов, ты создаешь Context, оборачиваешь приложение в Provider, и любой компонент может взять эти данные напрямую. Это простое, встроенное решение.

---

### ❓ "Какие компоненты переиспользуются?"

ProductCard (одна карточка) → используется в ProductGrid. ProductGrid → используется на главной, в категориях. Header/Footer → везде. AuthRequiredDialog → на защищенных страницах. Это показывает что я понимаю DRY и компонентную архитектуру.

---

### ❓ "Как обрабатываются ошибки?"

На фронте: try-catch, если запрос упал — показываем пользователю ошибку вместо краша. На бэке: возвращаем правильный HTTP код (400 если ошибка данных, 401 если не авторизован, 500 если сервер упал). Логируем в файл для отладки.

---

### ❓ "Архитектура БД?"

Таблицы: users, products, orders, order_items, favorites. Связи: One-to-Many (пользователь → заказы), Many-to-Many (пользователь ↔ товары через favorites). Индексы на user_id, product_id для быстрого поиска. Транзакции для консистентности при оформлении.
