## ЧАСТЬ 1: ЧТО ГОВОРИТЬ НА ЗАЩИТУ

Время: примерно 5-7 минут. Не спеши, говори уверенно.

### ВСТУПЛЕНИЕ (1-2 минуты)

Начни так:

> Привет всем. Я разработал веб-приложение SportMix для продажи спортивных товаров. Это полноценный проект с фронтенд-бэкенд архитектурой, который готов работать в боевых условиях.

Дальше кратко объясни, что делает приложение:

- Пользователи могут смотреть товары, добавлять их в корзину, оформлять заказы
- Есть личный кабинет, избранное
- Есть админка для управления каталогом и пользователями

### ТЕХНОЛОГИЧЕСКИЙ СТЕК (2-3 минуты)

Скажи что-то вроде:

> На фронтенде я использовал React и Vite. React потому что это наиболее популярный фреймворк, он позволяет разбить приложение на переиспользуемые компоненты. Vite я выбрал вместо Webpack потому что он намного быстрее - горячая перезагрузка работает за миллисекунды, а не за секунды. Это очень комфортно при разработке.

> Состояние приложения я управляю через Context API, встроенный в React. Это простое решение, которое отлично работает для приложений такого размера. Если бы проект растущий и становился большим, я бы перешел на Redux.

> На бэкенде используется Node.js с Express. Это быстрый и простой фреймворк. API обрабатывает все запросы от фронтенда - поиск товаров, работу с пользователями, заказами.

> Для развертывания я использую Docker - оборачиваю приложение в контейнеры. Это значит, что одинаково работает на моей машине, на машине коллеги и на сервере в интернете. На production развернул на платформе Render.

### КЛЮЧЕВЫЕ ФИШКИ (1-2 минуты)

Расскажи что сделал:

> Приложение имеет полный набор функций для нормального интернет-магазина. Каталог товаров, поиск, система рекомендаций. Корзина, оформление заказа, история заказов в профиле.

> На уровне оптимизации - поиск реализован с debouncing'ом, то есть не каждый символ вызывает запрос на сервер, а только после того как пользователь перестанет вводить. Это сберегает трафик и нагрузку.

> Адаптивный дизайн - нормально выглядит и на мобильном, и на компьютере.

### ЗАКЛЮЧЕНИЕ (30 секунд)

> В целом, этот проект показывает, что я понимаю полный цикл разработки - от дизайна компонентов на фронтенде до архитектуры API на бэкенде. Показывает опыт с Docker, облачным хостингом. Это практически полноценный реальный проект.

## ЧАСТЬ 2: ОТВЕТЫ НА ВОПРОСЫ

Вот что скорее всего спросят. Читай, запоминай суть.

---

### "Почему React, а не Vue/Angular?"

Просто скажи:

React популярнее всех. Его выбирает большинство компаний, поэтому навыки будут востребованы. Экосистема огромная - куча готовых библиотек. Разработка быстрая, отладка удобная.

Vue или Angular - тоже нормальные, но React на шаг впереди.

---

### "Почему Vite вместо Webpack?"

Webpack нужно долго настраивать, конфиг огромный. Vite просто работает из коробки. При разработке HMR очень быстрый - изменил код, и сразу видишь результат. Webpack медленнее. Для production сборки результаты похожи, но на разработке Vite комфортнее.

---

### "Как сделана аутентификация?"

На фронтенде:

- Форма входа берет логин и пароль
- Отправляет на бэкенд
- Бэкенд возвращает JWT токен
- Я сохраняю токен в localStorage
- Для защищенных страниц (заказы, профиль) проверяю наличие токена, если его нет - показываю диалог авторизации

На бэкенде:

- Проверяю логин/пароль
- Генерирую JWT токен
- Для каждого защищенного запроса проверяю что токен валидный

---

### "Как вы разделили код между фронтенд и бэкенд?"

Правило простое: все что касается логики и данных - на бэкенде. Все что касается интерфейса - на фронтенде.

Бэкенд:

- Валидация данных
- Доступ к БД
- Бизнес логика
- Безопасность

Фронтенд:

- UI компоненты
- Валидация форм на клиенте (для быстрого feedback)
- Управление состоянием приложения

Бэкенд не доверяет фронтенду - все переделает валидацию. Фронтенд тоже может валидировать, чтобы пользователю не приходилось ждать ответа от сервера.

---

### "Как работает поиск товаров?"

Я использую debounce. Это значит:

- Пользователь печатает
- Код ждет 500 миллисекунд после последней буквы
- Потом отправляет запрос на бэкенд
- Результаты приходят и отображаются

Это экономит запросы. Если бы я отправлял запрос при каждой букве, было бы много лишних запросов.

---

### "Насколько безопасно приложение?"

Безопасность на разных уровнях:

- CORS - бэкенд разрешает запросы только с правильных адресов
- JWT токены вместо простого хранения пароля
- Пароли на бэкенде хешируются bcrypt'ом, не хранятся в открытом виде
- HTTPS на production
- На бэкенде я всегда переделываю валидацию, даже если фронтенд уже проверил
- Токены можно хранить в HttpOnly cookies - это безопаснее чем localStorage

---

### "Как вы развертывали приложение?"

Локально просто:

```
docker-compose up
```

Docker Compose поднимает два контейнера - фронтенд и бэкенд. Все зависимости уже внутри контейнеров, ничего не конфликтует с системой.

На production я использовал Render. Там просто залил репозиторий на GitHub, и Render смотрит за изменениями. Как я push'ю - Render автоматически пересобирает приложение и деплоит.

---

### "Какие были сложности?"

Честно: CORS ошибки поначалу, пока я не понял как их правильно конфигурировать. State management - Context API работает, но если б приложение было побольше, пришлось бы на Redux переходить. Оптимизация Vite бандла. Мобильная версия - долго доделывал.

---

### "Что вы выучили?"

Полный стек - от фронтенда до бэкенда. Docker и как контейнеры работают. Как архитектуру проектировать. REST API. Security. Как деплоить на облако. Git и версионирование.

По факту это был мой первый реальный проект где я от нуля до конца все сам сделал.

### "Какие улучшения можно добавить?"

Парочку идей:

- Payment integration (Stripe/PayPal) для реальных платежей, сейчас это только эмуляция
- Поиск может быть медленнее если товаров много. Тогда нужен Elasticsearch
- Real-time уведомления через WebSocket - когда заказ обновляется, пользователь сразу видит
- Analytics - отслеживать какие товары популярнее, поведение пользователей
- Тесты - сейчас нет unit тестов, E2E тестов. При масштабировании это обязательно
- ML-рекомендации вместо случайных товаров

---

### "Почему Docker?"

Простой ответ: одна среда везде. Я разрабатываю на своем ноутбуке, коллега запускает на своем ноутбуке - всегда одинаково. Потом на production сервере - снова одинаково.

Без Docker я устанавливаю зависимости прямо на машину, может быть конфликт версий. С Docker все внутри контейнера, ничего не конфликтует.

---

### "Почему Node.js для бэкенда?"

Я уже знал JavaScript с фронтенда. Node.js позволяет использовать тот же язык. Экосистема NPM огромная - для любого нужна есть библиотека.

Express.js это минималистичный фреймворк, все что нужно есть, лишнего нет. Non-blocking I/O - может обработать много запросов одновременно.

---

### "Как вы тестировали?"

Во время разработки я постоянно проверял вручную. ESLint мне показывает если плохо написал код. Через DevTools браузера дебагил фронтенд. Постман'ом тестировал API.

Идеально нужны автоматические тесты - Jest, React Testing Library, E2E тесты на Cypress. Я их не делал потому что времени не было, но знаю как их писать.

---

### "Что такое Context API?"

Context API встроена в React. Это способ хранить данные которые нужны многим компонентам, не передавая их через пропсы.

Например, у меня есть `AppProvider` который оборачивает все приложение. Внутри он хранит информацию о текущем пользователе, товарах в корзине, любимых товарах. Любой компонент может взять эти данные напрямую из Context, не нужно передавать их через 5 слоев пропсов.

---

### "Какие компоненты переиспользуются?"

ProductCard - карточка одного товара, используется везде где товары выводятся.
ProductGrid - сетка товаров, используется на главной, в каталоге.
Header/Footer - на всех страницах.
AuthRequiredDialog - всплывает если пользователь не авторизован.

Это показывает что я понимаю принцип DRY - не повторяй код.

---

### "Как обрабатываются ошибки?"

Фронтенд: try-catch блоки, если запрос упал - показываю юзеру понятное сообщение вместо крашей.

Бэкенд: возвращаю нужный HTTP код (400 если ошибка клиента, 401 если не авторизован, 500 если ошибка сервера). Логирую ошибки чтобы потом отладить.

---

### "Как устроена БД?"

Таблицы: users, products, orders, order_items, favorites.

users - хранит пользователей с хешированными паролями.
products - товары с ценой, описанием, картинкой.
orders - заказы, связаны с пользователем.
order_items - товары в заказе.
favorites - какие товары лайкнул пользователь.

Индексы на часто запрашиваемых полях чтобы быстро искать.
